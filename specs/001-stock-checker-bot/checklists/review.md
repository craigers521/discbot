# Requirements Quality Review Checklist: Stock Checker Bot

**Purpose**: Validate the quality of the written requirements — not the implementation. Items are "unit tests for English": they check whether the spec, plan, contracts, and data model state their requirements completely, clearly, consistently, measurably, and with full scenario coverage, before implementation is reviewed.
**Created**: 2026-11-18
**Feature**: [spec.md](../spec.md) · [plan.md](../plan.md) · [contracts/](../contracts/) · [data-model.md](../data-model.md)
**Focus**: Full coverage — security & access control, alert correctness & reliability, operational resilience & edge cases, management API & contract consistency. Depth: standard. Audience: reviewer, at PR time.

**Note**: This custom checklist is generated by the `/speckit.checklist` command based on feature context and requirements.
**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.
**Marker Semantics**: `[x]` means the criterion has been reviewed and satisfied for requirements quality. It does not mean implementation work is complete.

## Security & Access Control

- [x] CHK001 - Are owner-authorization requirements specified for every management operation (list, add, remove, modify, cadence) on both interfaces, including configuration changes, or only for watch-list mutations? [Completeness, Spec §FR-010, §FR-017] — **Satisfied as-is**: FR-010 covers "ALL watch-list **and configuration** management"; discord contract gates every management interaction (including view); management-api contract gates every `/api/*` endpoint except the stateless health probe.
- [x] CHK002 - Is "rejected" for non-owner commands defined precisely enough to verify: does the requirement state that neither the watch list nor the configuration is altered **or read** by a rejected interaction, and that the rejection itself is owner-visible (FR-015)? [Measurability, Spec §SC-007, §FR-010, §FR-015] — **Acceptance decision**: rejection is ephemeral to the *invoking* user (contract: fixed text `❌ Not authorized…`, "no state is read for or altered"); FR-015 is satisfied by the clear error-with-reason delivered to the command's issuer. An owner-channel post per non-owner click is deliberately out of scope (spam; leaks who attempted access). Verifiable property: 100% rejected + zero state read or altered (SC-007).
- [x] CHK003 - Is the boundary of the shared-secret gate unambiguous: the spec gates "all dashboard and management API operations" (FR-020), while the contract serves the static shell (`/`, `/static/*`) and `GET /api/health` without a token — is that exemption stated in the spec, or is it a contract-only interpretation of "operations"? [Consistency, Spec §FR-020, Contract: management-api §Authentication] — **Resolved by rev-3 spec amendment**: FR-020 now defines "operations" = the management operations enumerated in FR-014; the stateless static shell and any public health indicator exposing no watch-list data or secrets are not operations. Contract exemptions are now spec-stated.
- [x] CHK004 - Are requirements defined for what happens when the shared secret is changed after deployment (e.g., a token previously stored in the dashboard's localStorage becomes invalid) — including how the owner regains dashboard access? [Gap, Spec §FR-020, Contract: management-api] — **Acceptance decision**: recovery is fully specified at contract level — stale token ⇒ `401` ⇒ dashboard clears storage and re-prompts ⇒ owner enters the new token (management-api §Authentication + dashboard flow; SC-008 guarantees no state change). Deployment-ops detail; no spec narration required.
- [x] CHK005 - Is the startup behavior for missing, empty, or malformed required credentials (Discord token, owner id, management channel id, webhook URL, shared secret) specified as a requirement — and is fail-fast (rather than silent defaults) the specified behavior, or only a data-model decision? [Gap, Spec §Assumptions "Secrets via environment", Data Model §5] — **Resolved by rev-3 spec amendment**: new edge case "Missing deployment credentials" (fail fast, error names the credential, no silent defaults) — matches data-model §5 and T006.
- [x] CHK006 - Is "the configured webhook destination fails to accept notifications" (FR-016) defined with specific, verifiable conditions (which HTTP outcomes, transport errors, or timeouts count), consistent with the "Invalid webhook destination" edge case? [Clarity, Spec §FR-016, Edge Cases] — **Satisfied as-is**: contract defines delivery failure = non-2xx **or** transport error (10 s timeout ⇒ transport failure); "invalid or revoked" (404 ⇒ non-2xx) is consistent with the edge case; failure is surfaced to the owner via the management channel.
- [x] CHK007 - Do the authorization requirements consistently cover every Discord interaction surface — buttons, select menus, **and** modal submits — across FR-010, FR-017, US2 scenario 4, and the Discord contract's authorization rule? [Consistency, Spec §FR-010, §FR-017, US2-4, Contract: discord §Authorization] — **Satisfied as-is**: FR-017 explicitly names "buttons, select menus, modals" and requires per-interaction user attribution for authorization; contract: "Every management interaction is checked" + flow summary "non-owner: [**any** management interaction]" (covers modal submits).

## Alert Correctness & Reliability

- [x] CHK008 - Is the exactly-once alert requirement (FR-008) reconciled with the "Invalid webhook destination" edge case: if delivery fails and is surfaced, does the spec state whether a retry is permitted, or whether "at most one" counts delivery *attempts* — or is "no silent re-alert" a contract-only rule? [Conflict, Spec §FR-008, Edge Cases, Contract: discord §Outbound] — **Resolved by rev-3 spec amendment**: no-retry clause appended to the edge case — failed delivery is surfaced once as an operational (FR-016) notice, **not** retried as a restock notification; FR-008 counts transitions; the status update stands. Matches data-model §6 (dedup state = persisted status) and contract.
- [x] CHK009 - Are the two delivery-latency statements consistent and jointly measurable: SC-002 (notification delivered within 1 minute of the *detecting check*) vs. the "Restock between checks" edge case (alert arrives within one cadence interval of the *actual restock*) — is each clock explicitly named in its own requirement? [Consistency, Measurability, Spec §SC-002, Edge Cases] — **Satisfied as-is**: both clocks are named (SC-002: "the check that detected the transition"; edge case: "the actual restock"); jointly satisfiable — restock at T ⇒ detected ≤ T + cadence ⇒ delivered ≤ +60 s.
- [x] CHK010 - Is the no-alert-on-add rule unambiguous for every path by which a product reaches "in stock" from its initial "unknown" state (US1-4, Assumption "No immediate alert on add") — i.e., is there exactly one specified rule, consistently referenced, governing first-determination alerts? [Clarity, Spec US1-4, Assumptions, Data Model §6] — **Satisfied as-is**: exactly one rule — alert only on a persisted `out_of_stock → in_stock` transition; first determination from `unknown` (either direction) never alerts. Referenced consistently: US1-4, Assumption "No immediate alert on add", data-model §6, T014.
- [x] CHK011 - Is the notification content requirement complete and consistent: FR-007 mandates label + URL, the "Notification content" assumption adds the detection time, and the contract posts all three — is the timestamp a mandated requirement, an assumption, or optional? [Consistency, Spec §FR-007, Assumptions "Notification content", Contract: discord §Outbound] — **Satisfied as-is**: label + URL are FR-007 MUSTs; the detection time is a spec **Assumption** ("Notification content" — includes all three, nothing else in v1); the contract posts exactly these three. Nothing is marked optional; fully consistent.
- [x] CHK012 - Are the ordering/atomicity requirements between persisting a status transition and sending the alert stated in the spec, such that SC-002 (timely alert), SC-005 (no duplicate alert after restart), and the webhook-failure edge case (no silent re-alert) can all be satisfied simultaneously? [Ambiguity, Spec §SC-002, §SC-005, Edge Cases, Data Model §6] — **Acceptance decision**: the spec states the verifiable *outcomes* (SC-002, SC-005, no-silent-re-alert) and they are non-contradictory; the ordering mechanism (apply+persist transition → send; send-failure keeps the transition; dedup state = persisted status) is fixed in data-model §6 + contract and is the only ordering satisfying all three. Ordering is a design-level concern, like the CHK017 lock rule.
- [x] CHK013 - Are the requirements for simultaneous multi-product restocks complete: separate notification per product, plus any stated position on ordering, interleaving, or volume in a single cycle? [Completeness, Spec Edge Cases "Multiple products restocking at once"] — **Satisfied as-is**: edge case states separate notification per product, "not deduplicated or batched" (volume/interleaving position); ordering follows the FR-018 sequential watch-list walk; one notification per restocked product.

## Operational Resilience & Edge Cases

- [x] CHK014 - Is it specified in the spec whether "unknown" determinations count toward the consecutive-failure threshold (FR-016), or only fetch errors — the spec treats them separately (FR-012), while the data model and contract group both for the threshold? [Ambiguity, Spec §FR-012, §FR-016, Edge Cases, Data Model §6] — **Satisfied as-is**: Assumption "Stock-detection hybrid (clarified)" states unknown "is treated like a failed determination … repeated unknown results trigger the repeated-failure notification"; FR-012 includes "unrecognizable page content" among failed fetches. Consistent with data-model §2/§6 and the contract.
- [x] CHK015 - Is the repeated-failure notification threshold a specified requirement with a defined value and configurability, or is "for example, 10 consecutive failures" (spec) an illustration left to an unspecified default (contract: `FAILURE_THRESHOLD`, default 10)? [Clarity, Spec Edge Cases "Repeated check failures", Data Model §5] — **Satisfied as-is**: the requirement is specified (FR-016 + edge case); the value **is** defined (default 10) and configurable (`FAILURE_THRESHOLD` env, data-model §5) — not "unspecified". The spec's "for example, 10" matches its own "assumed value" style (cf. "Sensible defaults").
- [x] CHK016 - Are recovery requirements defined for a corrupt durable state file at startup: FR-009 requires persistence and automatic resume, but only the data model specifies rename-and-start-fresh — is the resulting watch-list data loss an accepted, stated requirement? [Gap, Spec §FR-009, Data Model §7] — **Resolved by rev-3 spec amendment**: new edge case "Corrupt durable state at startup" — start fresh, preserve the unreadable store (move aside), never overwrite/delete it — so the owner can inspect or restore. Matches data-model §7 / research §7.
- [x] CHK017 - Is the concurrent-interface-use requirement ("the bot MUST end with a consistent watch list — no lost updates and no duplicate entries") defined precisely enough to verify, including which operation wins when two simultaneous operations conflict on the same product? [Clarity, Measurability, Spec Edge Cases "Concurrent interface use", Data Model §6] — **Satisfied as-is**: outcome specified in the spec; mechanism = lock serialization (data-model §6) — the winner is lock order, the loser re-validates against the updated state (⇒ `duplicate_url`/`not_found`), final state = serial application in some order. Verifiable via T010's concurrency test.
- [x] CHK018 - Are requirements specified for Discord gateway disconnection and reconnection (re-posting the control message, delivering owner notices that were pending), or is that behavior contract-only (self-healing on reconnect, one retry)? [Gap, Spec §FR-017, Contract: discord] — **Resolved by rev-3 spec amendment**: new edge case "Gateway disconnect" — auto re-establish, re-post the control message, undelivered notices retried on reconnect (at least once), never dropped. Matches contract + discord.py default reconnection (no scope added).
- [x] CHK019 - Are requirements specified for the management channel becoming unavailable (deleted, bot removed from the server) — the control message, operational notices, and webhook-failure surfacing all depend on it? [Gap, Spec §FR-016, §FR-017, Contract: discord] — **Resolved by rev-3 spec amendment**: new edge case "Management channel unavailable" — keep checking + webhook alerting (core flow is channel-independent), log failures, re-post the control message when available again.
- [x] CHK020 - Is the owner-visible representation of the "unknown" status specified: FR-003 requires showing each product's "latest determined stock status" — is "unknown" displayed, and with what explanation (e.g., not yet determined vs. layout mismatch)? [Clarity, Spec §FR-003, §FR-006, Contract: discord §Status emoji legend] — **Satisfied as-is**: "unknown" is displayed as `⚪ unknown (not determined yet)` (contract legend + dashboard badge); since unknown determinations never change status (FR-012 / data-model §6), `last_status = unknown` can only ever mean "not yet determined" — the explanation is always accurate.
- [x] CHK021 - Is detection latency (a restock is detected within one cadence interval of the actual restock) captured as a measurable success criterion, or does it appear only as a narrative edge case with no verifiable outcome? [Completeness, Spec Edge Cases "Restock between checks", Success Criteria] — **Resolved by rev-3 spec amendment**: now **SC-009** — "A restock is detected on the next scheduled check after it occurs — detection latency is at most one cadence interval from the actual restock."

## Management API & Contract Consistency

- [x] CHK022 - Is the check-now operation (`POST /api/check-now`, justified in the plan's Constitution Check) traceable to a spec requirement (FR or user story), or is it an addition that exists only in the plan and contract? [Traceability, Gap, Plan §Constitution Check, Contract: management-api] — **Accepted (recorded)**: it *is* a plan/contract-level addition, justified in plan.md Constitution Check ("only practical way to validate SC-001/SC-002 end-to-end without waiting a full cadence interval") — the constitution's sanctioned simplicity-justification path; it performs no action the scheduler would not itself perform.
- [x] CHK023 - Is the cadence **ceiling** specified in the spec: FR-011 requires only a minimum, US3 scenarios cover below-minimum and malformed values only, yet the contract enforces `MAX_CADENCE_MINUTES` (1440) — is the ceiling a requirement, or an untraced contract addition? [Gap, Conflict, Spec §FR-011, US3, Contract: management-api `PUT /api/config`] — **Resolved by rev-3 spec amendment**: FR-011 now also enforces a **maximum** cadence (sanity upper bound, assumed 24 h) with rejection + explanation; US3 scenario 4 (above-maximum) added. Tests T033/T034 already covered above-ceiling rejection.
- [x] CHK024 - Is URL immutability ("changing the URL = remove + add") specified as a requirement anywhere, or is it a contract-only PATCH rule — FR-004 requires modifying "at minimum, its label" but never states whether the URL itself may be modified? [Gap, Spec §FR-004, Contract: management-api `PATCH`] — **Resolved by rev-3 spec amendment**: FR-004 now states the URL is immutable — changing the tracked page is remove-and-add, and a re-added product starts from an undetermined status (ties the rule to US1-4's no-alert-on-add). Consistent with the PATCH contract, data-model uniqueness key, and quickstart §5.
- [x] CHK025 - Is a "valid product page address" (US4-5) defined in the spec with specific criteria (scheme, host) consistent with the data model's validation rules (absolute http(s), non-empty host, normalization)? [Clarity, Consistency, Spec US4-5, Data Model §2] — **Resolved by rev-3 spec amendment**: FR-001 now defines a valid product page address = absolute `http(s)` URL with a non-empty host — US4-5 is verifiable from the spec. Normalization details remain in data-model §2 (see CHK040).
- [x] CHK026 - Are field-validation requirements (label 1–100 chars; indicators ≤200 chars, case-insensitive substring matching) traceable to a spec requirement, or are they data-model/contract decisions with no spec basis? [Traceability, Gap, Spec §FR-001, §FR-006, Data Model §2] — **Accepted (recorded)**: the numeric limits and substring-matching semantics are validation details derived from FR-001 ("short label") and FR-006 (text/element indicators); recorded in data-model §2 and research §6. The spec deliberately fixes no exact numbers (technology-agnostic); FR-015 guarantees the owner sees a clear reason for every rejection.
- [x] CHK027 - Is it unambiguous that adding a product is supported only through the dashboard (FR-001 parenthetical) with no Discord add control — do US2, FR-001, and both contracts state this consistently? [Consistency, Spec §FR-001, US2, Contract: management-api, Contract: discord] — **Satisfied as-is**: FR-001 parenthetical ("free-text URL entry is available only through the dashboard"), US2, discord contract (the "Add product" control is a **link button** to the dashboard URL, not an add operation), and API contract (`POST /api/products` is the dashboard's path) all agree.
- [x] CHK028 - Are the error/confirmation requirements (FR-015) complete across every failure mode in the contract (`invalid_url`, `invalid_label`, `invalid_indicator`, `invalid_cadence`, `duplicate_url`, `not_found`, `cycle_in_progress`) — is each contract error situation traceable to a spec requirement or scenario? [Completeness, Traceability, Spec §FR-015, US3, US4, Contract: management-api] — **Satisfied as-is**: all seven trace to spec — `invalid_url`→US4-5; `invalid_cadence`→US3-2/3 (+ rev-3 scenario 4); `duplicate_url`→US4-6 + "One product per URL"; `invalid_label`/`invalid_indicator`→FR-001/FR-006; `not_found`/`cycle_in_progress`→FR-015 (clear error for every operation) + FR-018 (no parallel cycles). FR-015 is the blanket requirement.
- [x] CHK029 - Is the dashboard refresh model (Assumption: re-render on load and after each operation; no auto-refresh or push) consistent with FR-003's requirement that the dashboard show the "latest determined stock status" and US4 scenario 2's "identical result" across interfaces? [Consistency, Spec Assumptions "Dashboard refresh model", §FR-003, US4-2] — **Satisfied as-is**: "latest determined status" = the shared store's value at query time (not live); the refresh model (re-render on load/after operation) is a stated assumption; US4-2 concerns operation *results* against one source of truth, not live sync. No contradiction.

## Non-Functional Requirements

- [x] CHK030 - Are the performance targets (SC-006: 25 products at a 5-minute cadence, full sequential cycle within one cadence interval) verifiable as written — is "under normal network conditions" qualified with specific bounds (per-fetch timeout, pause, headroom)? [Measurability, Spec §SC-006, §FR-018, Plan §Performance Goals] — **Satisfied as-is**: "normal network conditions" is operationalized in plan Performance Goals — 15 s per-fetch timeout + 2 s pause ⇒ worst-case-normal ≈ 25 × 7 s ≈ 175 s < 300 s (headroom made explicit); quickstart scenario 11 is the verification. The spec stays technology-agnostic, as intended.
- [x] CHK031 - Is the politeness requirement "does not issue more requests to a retailer than the configured cadence implies" (Assumption) measurable — is there a per-retailer request-rate requirement, or only a global minimum cadence (FR-011) that bounds average load? [Measurability, Spec Assumptions "Polite fetching", §FR-011] — **Satisfied as-is**: measurable decomposition — each watched URL is fetched ≤ 1×/cycle (FR-018 single sequential walk), cycles are ≥ MIN_CADENCE apart (FR-011), and no cycles overlap (FR-018) ⇒ per-retailer request rate ≤ (that retailer's product count) per cadence interval.
- [x] CHK032 - Are the fetch timeout and inter-request pause values specified as requirements with defined failure semantics (timeout ⇒ failed check per FR-012), or are they unspecified defaults (15 s / 2 s) recorded only in the data model? [Clarity, Spec Edge Cases "Very large or slow pages", §FR-018, Data Model §5] — **Satisfied as-is**: the requirements **with failure semantics** are in the spec (FR-012: timeout ⇒ failed check; FR-018: short pause between requests; "Very large or slow product pages" edge case); only the *values* (15 s / 2 s) are env-configurable data-model defaults — the same "assumed value" pattern as cadence.
- [x] CHK033 - Is the absence of availability/uptime requirements (beyond restart persistence in FR-009 and SC-005) an intentional, stated scope decision rather than an unstated omission? [Scope Boundary, Gap, Spec §FR-009, Success Criteria] — **Resolved by rev-3 spec amendment**: new assumption "No availability targets in v1" — single personal container, no uptime target/watchdog/self-healing beyond the gateway-reconnect and channel-unavailable edge cases; owner restarts; state continuity per FR-009/SC-005.
- [x] CHK034 - Are observability requirements specified — how the owner learns that the bot itself is malfunctioning (gateway down, notices undeliverable, cycle stalled) — beyond FR-016's management-channel notices, which themselves depend on the gateway? [Gap, Spec §FR-016, Contract: discord §Outbound] — **Resolved by rev-3 spec amendment**: new edge case "Bot malfunction visibility" — on gateway/channel unavailability the bot keeps checking + alerting and MUST expose a public health indicator on the port (no watch-list data, no secrets) reporting at minimum gateway-connected and cycle-in-progress. The contract's `GET /api/health` satisfies it.
